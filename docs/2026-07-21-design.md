# SongForge-MCP — Design

Date: 2026-07-21 (revised same-day, second session)
Status: v1 scope finalized through discussion. Ready for implementation
planning.

## Motivation

User produces EDM/pop/rock and is frustrated by two real, recurring
costs: paying for vocal sample packs that have limited or awkwardly
cut-off lyrics with no way to change them, and the expense/coordination
overhead of hiring a real vocalist for every track. Goal: generate
royalty-controlled vocal stems locally, with full control over the
lyrics, that can be dropped straight into a REAPER project.

## The intended workflow

This is prompt-driven, not melody-file-driven. The target interaction,
inside a Claude Desktop/Code session that also has `reaper-mcp`
connected:

> "I need vocals from bar 1 to bar 10, about sadness and being alone,
> in the style of Illenium. You choose the bpm and key."

1. Claude reads the open REAPER project via reaper-mcp's existing read
   tools (`get_track_instruments`, `project_get_info`, `item_get_all`)
   to learn key/BPM/structure/section boundaries.
2. Claude works out lyrics and an explicit vocal melody (pitch +
   rhythm per syllable) that fits the requested mood/style/section —
   **vocal line only**, no instrumentation, no backing track. This is
   composition reasoning, and it lives entirely in Claude's side of the
   conversation, not in this server.
3. Claude proposes the lyrics (and, on request, describes the melody)
   back to the user for confirmation before rendering anything.
4. Once confirmed, Claude calls this server's `synthesize_vocal` tool
   with the fully explicit result (notes, lyrics, bpm, voicebank).
5. This server renders a **vocal-only WAV stem** (no bass/synths/other
   backing elements — that would be a different, unwanted default) and
   returns it plus structured diagnostics.
6. Claude uses reaper-mcp's existing tools to import the stem into the
   project, positioned and labeled correctly.

## Architecture

**Two separate MCP servers, one Claude session, no new coupling code
between them.**

- **This project (SongForge-MCP)** — a standalone server exposing
  vocal synthesis given an explicit melody + lyrics + voicebank
  selection, plus supporting tools (voicebank listing, score
  validation). No project awareness, no music-theory logic, no
  composition decisions — but *not* a dumb fire-and-forget box either:
  see "Tool contract & feedback loop" below.
- **reaper-mcp** (`D:\DansProject\Reaper-MCP`, sibling project) — stays
  completely unchanged. Its existing tools bring the generated WAV into
  a REAPER project, correctly labeled and aligned.
- **Claude does all the composing.** Lyrics, melody (pitch/rhythm),
  style interpretation, bpm/key choice (when the user doesn't specify),
  and the confirm-with-user loop all happen in conversation. The
  synthesis server never invents musical content — it only renders what
  it's explicitly told to sing.

This keeps a clean boundary: creative judgment stays in the
conversation (where the user can steer it), mechanical rendering stays
in this codebase (where it can be tested deterministically).

## Why not [other options considered]

- **OpenUtau** — researched specifically for headless/CLI rendering.
  Its documented path is GUI-only (File → Export Audio); can't be
  driven by an MCP tool call. Ruled out for the render path.
- **Synthesizer V** — 2026 quality gold-standard, but closed and paid;
  conflicts with "local, free, full control." Noted as a fallback only
  if DiffSinger quality proves inadequate.
- **YourTTS** (prior attempt at `D:\DansProject\YourTTS_Project`) —
  voice-cloning TTS, not melody-controlled singing synthesis. Wrong
  technology for this problem regardless of that attempt's issues.
- **Fish Speech / CosyVoice2 / IndexTTS-2** — TTS/voice-cloning models
  surfaced in "best singing synthesis" listicles; confirmed not true
  melody-controlled singing tools. Ruled out explicitly.

## Prior art check

Before finalizing, surveyed comparable projects to catch anything that
should change the design. Nothing did — confirms the choices above
rather than revising them:

- **No usable existing DiffSinger wrapper.** `openvpi/DiffSingerMiniEngine`
  (headless, MIDI-less mode) is the closest match but archived/dead
  since Feb 2024. Confirms building our own subprocess+`.ds` integration
  is necessary, not a reinvented wheel — no dependency adopted from
  this.
- **No alternative engine beats DiffSinger here.** VISinger2 scores
  higher on one MOS comparison but has no stronger English story;
  NNSVS is Japanese-corpus-centric and itself borrows DiffSinger's
  diffusion code. Technology choice stands.
- **ElevenLabs' MCP server** (TTS, not singing — weak direct comparison)
  showed one useful *pattern*, not code or a dependency: a single tool
  offering both simple and granular control. Adopted as the
  `expressive_params?` design above — our own implementation, nothing
  borrowed or wrapped.

## Technology

**DiffSinger (openvpi's actively-maintained fork).** Confirmed via
direct research into openvpi's repo/docs:

- **Not pip-installable** — clone-and-run. `songforge-mcp` depends on
  a separately-cloned DiffSinger checkout (path configured at install
  time) and **subprocesses out** to it rather than importing it as a
  library. Conceptually similar to reaper-mcp's external-process
  bridge, but simpler — one-shot CLI calls, no persistent daemon or
  heartbeat needed (DiffSinger isn't a long-running app like REAPER).
- **Input format:** `.ds` JSON files. Required fields: `ph_seq`
  (phoneme sequence), `ph_num` (word→phoneme grouping), `note_seq` /
  `note_slur` (the melody). Optional explicit `ph_dur`, `f0_seq`
  (pitch curve), and variance params (energy/breathiness/voicing/
  tension) — if omitted, the variance model predicts them.
- **Inference is two subprocess stages:**
  ```
  python scripts/infer.py variance song.ds --exp <experiment>
  python scripts/infer.py acoustic song.ds --exp <experiment>
  ```
  Vocoder: NSF-HiFiGAN, 44.1kHz output.
- **Requirements:** Python ≥3.10, PyTorch ≥2.4.0 (installed separately,
  matched to CUDA version), remaining deps via
  `pip install -r requirements.txt` inside the clone.
- **Hardware:** RTX 5070, 12GB VRAM. No official inference VRAM figure
  published, but docs confirm inference has a documented **CPU
  fallback path** ("training requires CUDA; inference can run on CPU
  at a slower rate") — a model with a viable CPU path is not
  VRAM-hungry. 12GB should be comfortable; treat as low-risk, not a
  hard-confirmed number.
- Sources: openvpi/DiffSinger `docs/GettingStarted.md`, DeepWiki
  system-architecture and installation pages (checked this session).

## Voicebank

No official English voicebank from openvpi (their releases skew
Mandarin/Opencpop), but real community English voicebanks exist:
**Raine Rena**, **Hoshino Hanami**, **Nishiren Gard**, and the
**LUNAI Project** (markets itself as consent-based/"ethical" voice
sourcing — worth checking first given this project's own stance on
rights-clean data). None of these have had their actual license terms
verified yet — **that verification, plus picking one, is a concrete
first implementation task**, not resolved by this design doc.

## Tool contract & feedback loop

`synthesize_vocal(notes, lyrics, bpm, voicebank, expressive_params?)
-> {wav_path, diagnostics}` is the core tool. It is explicitly **not**
a dumb fire-and-forget box:

- **Simple mode vs. granular mode, same tool.** `expressive_params`
  (pitch curve / energy / breathiness / tension) is optional — maps
  directly onto DiffSinger's own `.ds` design, where the variance
  model predicts these if omitted. Claude can call with just
  notes+lyrics for a normal case, or supply explicit curves when it
  wants precise control (e.g. reacting to a previous take's
  diagnostics). No new capability to build — this is exposing what
  DiffSinger's pipeline already supports, not composing on the
  server's behalf.
- **Rich structured diagnostics in every response** — weak
  phoneme/note alignment, notes outside the voicebank's comfortable
  range, actual vs. requested duration, loudness/clipping flags — so
  Claude can see *why* something sounds off and decide whether to
  retry with adjusted notes or ask the user, without re-listening to
  the audio itself.
- **Typed, specific errors**, same pattern as reaper-mcp's
  `ReaperMCPError`/`ErrorCode`: e.g. `NOTE_OUT_OF_RANGE`,
  `PHONEME_NOT_FOUND`, `LYRIC_NOTE_COUNT_MISMATCH` — specific enough
  that Claude can self-correct instead of getting a generic failure.
- **Supporting tools:** `list_voicebanks` (range, language, style
  tags — so Claude picks an appropriate one) and a fast `validate_score`
  pre-check (catch alignment problems before spending time on full
  two-stage synthesis).
- **An injected instructions doc** (`instructions/00_core.md`, same
  role as reaper-mcp's), teaching the calling LLM the note/phoneme
  format, good-practice patterns for style-matching, and a staged
  reasoning approach for the composition step — mood/style text to an
  explicit note sequence first, then separately to expressive delivery
  choices — the same stage-split used in current melody-from-text
  research (MelodyLM), referenced here as a reasoning pattern only, not
  as a dependency.
- **Explicit boundary:** the server reports problems richly but does
  **not** auto-retry or auto-adjust parameters itself. Retries are a
  Claude-driven loop informed by this server's diagnostics — keeps
  musical judgment entirely in the conversation, consistent with "no
  composition logic in this codebase."

## Repo conventions

Mirrors the existing sibling projects (`Reaper-MCP`, `AudacityMCP`)
exactly, for consistency and because the pattern is proven:

```
songforge_mcp/
├── main.py                  # FastMCP entry point
├── tool_registry.py         # Auto-discovers tools/ modules (pkgutil walk)
├── diffsinger_client.py     # Subprocess wrapper: builds .ds, runs variance+acoustic
├── instructions/
│   └── 00_core.md           # Injected system-prompt instructions
└── tools/                   # synthesize_vocal, list_voicebanks, validate_score

songforge_mcp_shared/
├── constants.py             # Paths, timeouts, safety limits
├── error_codes.py           # SongForgeMCPError + ErrorCode enum
└── protocol.py              # .ds file building/parsing helpers

docs/
├── ARCHITECTURE.md
├── INSTALLATION.md          # incl. DiffSinger checkout setup
└── TOOLS.md

install.bat / install.sh     # sets up DiffSinger checkout + its venv
tests/
CONTRIBUTING.md
CHANGELOG.md
```

## Scope

**In scope for v1:**
- `synthesize_vocal`, `list_voicebanks`, `validate_score` tools as
  described above, with rich diagnostics and typed errors.
- Pick + verify license terms for one English DiffSinger voicebank
  (LUNAI Project first look), use it as the shipped default.
- Subprocess integration with a separately-cloned DiffSinger checkout
  (`.ds` file building, two-stage invocation, output parsing).
- Professional repo scaffold matching reaper-mcp/AudacityMCP
  conventions, including an injected instructions doc.
- Stateless synthesis — no project awareness inside this server, no
  persistence beyond the rendered WAV.

**Explicitly out of scope for v1** (deferred, not rejected):
- **Fine-tuning on personal Splice vocal libraries** (v2). User has
  multiple Splice vocal packs from different artists (e.g. "KARRA
  Presents Heather Sommer"), for **personal use only**. Hard rule
  carried forward: any fine-tuned model and its outputs stay local and
  personal, never bundled into anything shareable/public — the
  publicly-shared default config stays pretrained-voicebank-only, to
  keep the ambiguous-training-rights material (Splice licenses cover
  "use in a mix," not confirmed for "use as ML training data") fully
  contained to the user's own private use. Needs its own design pass:
  data prep (phoneme/pitch alignment per pack), per-vocalist data
  volume assessment (a single topline pack is likely thin — 20-60 min
  — for training from scratch, more viable for adapting a pretrained
  model), and training compute requirements (heavier than inference).
- Any melody/lyric composition logic *inside* this server — stays in
  Claude's reasoning per the architecture above.
- Voice-conversion layer (RVC/so-vits-svc) for a specific
  character/celebrity-adjacent voice — discussed and explicitly out of
  scope.
- Stem-analysis / auto-fill-missing-tracks and multi-MCP-server
  orchestration ideas — parked in reaper-mcp's `docs/FUTURE_IDEAS.md`,
  unrelated to this project's v1.

## Voice sourcing — read this before touching training data

Extensively discussed; survives into implementation intact:

- "Royalty-free for use in a produced track" and "cleared for AI
  training" are different permissions. Most sample-pack licenses grant
  the former, not the latter, and predate AI voice cloning as a
  mainstream concern — silence doesn't mean permission.
- Training on a specific identifiable real artist's voice without
  explicit rights, then releasing music built on it, carries real
  copyright/voice-likeness exposure — active, unsettled legal area.
- Blending multiple artists' voices does not resolve this — it
  multiplies the number of rights-holders whose material is used
  without authorization, rather than reducing exposure.
- **v1 decision (unchanged): generic pretrained voicebank, not
  custom-trained.**
- **v2 decision (new this session):** personal-use fine-tuning on the
  user's own purchased Splice vocal packs is accepted as a deliberate,
  scoped risk the user is choosing to take **for personal use only** —
  not a resolution of the underlying rights ambiguity. Never build
  toward a specific real/identifiable artist's voice for anything
  distributed or shared without resolving that properly first (ideally
  asking first, not after).
