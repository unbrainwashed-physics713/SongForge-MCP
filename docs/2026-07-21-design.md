# Vocal-Synth-MCP — Design

Date: 2026-07-21
Status: Scoped through discussion, not yet formally implemented. Continue
from here in a fresh session in this folder.

## Motivation

User produces EDM/pop/rock and is frustrated by two real, recurring
costs: paying for vocal sample packs that have limited or awkwardly
cut-off lyrics with no way to change them, and the expense/coordination
overhead of hiring a real vocalist for every track. Goal: generate
royalty-controlled vocal stems locally, with full control over the
lyrics, that can be dropped straight into a REAPER project.

This is explicitly **not** about AI composing melodies — the user was
clear on that repeatedly. It's a pure synthesis capability: given a
melody (which notes, what rhythm) and lyrics, produce a real sung vocal
performance as an audio stem.

## Architecture

**Two separate MCP servers, one Claude session, no new coupling code
between them.**

- **This project (Vocal-Synth-MCP)** — a standalone server exposing one
  core capability: synthesize a sung vocal stem from an explicit melody
  + lyrics + voicebank selection. No project awareness, no music-theory
  logic, no composition decisions of any kind. Pure input-in, audio-out.
- **reaper-mcp** (`D:\DansProject\Reaper-MCP`, sibling project, same
  session's primary work all of 2026-07-20) — stays completely
  unchanged. Its existing tools (`item_insert_media`, track
  creation/renaming, positioning) are what actually bring the generated
  WAV into a REAPER project, correctly labeled and aligned. No new
  reaper-mcp code needed for that.
- **Claude (the orchestrating AI) does all the "thinking."** When the
  user says something like "I need female vocals that sound amazing,"
  Claude reads the existing REAPER project via reaper-mcp's *existing*
  read tools (`get_track_instruments`, `project_get_info`, `item_get_all`)
  to understand key/BPM/structure, decides (or asks the user for) lyrics
  and a melody, calls this server's synthesis tool with the fully
  explicit result, then uses reaper-mcp to import it. All judgment calls
  happen in the conversation — the synthesis server itself never composes
  anything.

This resolves an early false choice in the discussion between "standalone
tool nobody would use outside a DAW" and "cram it into reaper-mcp and
bloat its lightweight dependency footprint." It's neither — a separate
codebase and dependency set, but functionally inseparable from the
REAPER workflow because Claude bridges the two servers in one
conversation.

## Why not [other options considered]

- **OpenUtau** (the obvious existing free frontend for DiffSinger-style
  synthesis, with a proper piano-roll melody+lyric workflow) — researched
  specifically for a headless/CLI/scriptable rendering mode. Found none;
  its documented rendering path is GUI-only (File → Export Audio). An MCP
  tool call can't click through a GUI, so this is out for the actual
  synthesis path, even though its UX ideas are worth referencing.
- **Synthesizer V** — still the 2026 quality gold-standard for
  MIDI-driven singing synthesis per current comparisons, but closed and
  paid — conflicts with the "local, free, full control" motivation that
  started this whole discussion. Noted as a possible fallback only if the
  DiffSinger integration proves too rough to reach acceptable quality.
- **YourTTS** (a prior, substantial attempt at
  `D:\DansProject\YourTTS_Project`, November 2025, which by its own file
  history hit real training/setup trouble — `TRAINING_HANG_DIAGNOSIS.md`,
  `PYTORCH_VERSION_FIX.md`, etc.) — different technology entirely. YourTTS
  is voice-cloning TTS (clone a *speaking* voice, make it say text), not
  melody-controlled singing synthesis. It was never going to solve this
  problem regardless of how that attempt went. Confirmed with the user
  that project was for narration/AI-companion use, and produced
  "sub-par" audio quality for that purpose anyway.
- **Fish Speech / CosyVoice2 / IndexTTS-2** — surfaced in some "best
  singing synthesis" listicles during research, but confirmed via
  further search to be text-to-speech/voice-cloning models, not true
  melody-controlled singing tools. Ruled out explicitly so they don't
  quietly become the wrong foundation later.

## Technology

**DiffSinger (openvpi's actively-maintained fork)**, driven directly
through its own Python inference pipeline — not through OpenUtau, for
the headless reason above. Refactored fork improvements over the
original: 44.1kHz output (vs 24kHz original), better vocoders
(NSF-HiFiGAN), controllable pitch/energy/breathiness parameters.

**Hardware:** confirmed against the user's actual machine — NVIDIA RTX
5070, 12GB VRAM. Comfortably above what local audio AI generally needs
(music-gen models typically want ~12GB minimum; TTS/voice work needs
far less). DiffSinger's own historical training requirements cited
2080Ti/3090-class GPUs; this machine is newer and sits in that same
capable tier. Inference (using an already-trained voicebank, not
training a new one) should be considerably lighter than that — not yet
confirmed with precise numbers, verify against openvpi's own docs before
finalizing the implementation plan.

## Scope

**In scope for v1:**
- A single MCP tool, shape TBD precisely but roughly:
  `synthesize_vocal(notes: [{pitch, start, duration}], lyrics: str per
  note/phoneme, bpm: float, voicebank: str) -> wav_path`
- Using an existing pretrained DiffSinger voicebank (openvpi community
  releases) — quality/style is whatever's actually available, not
  custom-tailored. Real listening-based research into what's actually
  out there for a fitting voice character is a needed next step, not yet
  done — earlier research confirmed the *technology* is legitimate but
  did not evaluate specific voicebank quality.
- Straightforward, stateless synthesis — no project awareness, no
  persistence beyond the rendered WAV.

**Explicitly out of scope for v1** (all deferred, not rejected):
- Any melody/lyric composition logic inside this server — lives in
  Claude's reasoning + reaper-mcp reads instead, per the architecture
  above.
- Training a *custom* voice. See "Voice sourcing" below — this needs
  its own resolution before it's revisited at all, and even then, worth
  scoping as a distinct piece of work, not bundled into v1.
- Any voice-conversion layer (RVC/so-vits-svc) for a specific
  character/celebrity-adjacent voice on top of the base synthesis.
  Discussed at length (see "Voice sourcing"); not part of this project's
  scope.
- The stem-analysis / auto-fill-missing-tracks idea (parked separately
  in reaper-mcp's `docs/FUTURE_IDEAS.md`) — related in spirit, not the
  same project.
- The multi-MCP-server orchestration/token-efficiency idea (also parked
  in reaper-mcp's `docs/FUTURE_IDEAS.md`) — explicitly deferred by the
  user until after this project has something working.

## Voice sourcing — read this before touching training data

This was extensively discussed and deserves to survive into a fresh
session intact, not get silently reconsidered.

- "Royalty-free for use in a produced track" and "cleared for AI
  training" are different permissions. Most standard vocal sample-pack
  licenses grant the former, not the latter, and most were written
  before AI voice cloning was a mainstream concern — silence on AI
  training doesn't mean permission.
- Training on a specific identifiable real artist's voice without
  explicit rights, then releasing music built on it, carries real
  copyright and voice/likeness-rights exposure — this is an active,
  unsettled area of AI law, not a hypothetical.
- "Open-sourcing the tool for free" does not address this at all — that
  affects monetization, not whether the underlying training data was
  used with permission. The tool/code being free is completely fine and
  unrelated; what matters is the training data's actual rights status.
- "Blend 3-4 artists' voices together so the output isn't attributable
  to one" does not resolve this either — it multiplies the number of
  individual rights-holders whose material is used without
  authorization rather than reducing exposure, and doesn't change
  whether using each of those recordings as training input was
  authorized in the first place.
- User does not currently have rights-clear training material (can't
  sing themselves; existing sample packs' AI-training rights status is
  unconfirmed/likely not granted). Decision reached: **v1 uses a generic
  pretrained voicebank, not a custom-trained voice.** The question of
  whose voice (if any) gets custom-trained later is explicitly deferred,
  not resolved — don't build toward a specific real artist's voice
  without that being properly resolved first (ideally: reaching out and
  asking *before* building anything, not after).

## Open questions for the next session

1. Actual DiffSinger score/input format — needs a real look at the
   openvpi repo's expected input (notes, phonemes, timing) to design the
   exact shape of `synthesize_vocal`'s parameters precisely.
2. Which specific pretrained voicebank(s) to ship with v1 — needs real
   listening evaluation, not assumed from documentation alone.
3. Exact MCP tool schema and error handling conventions — should follow
   reaper-mcp's own established patterns (structured `ReaperMCPError`-
   style errors, clear docstrings) for consistency, even though this is
   a separate codebase.
4. Packaging/dependencies — PyTorch + DiffSinger's own requirements are
   a real, heavy dependency set; decide install/setup story (this is
   exactly why it's a separate project from reaper-mcp's lightweight
   footprint).
5. Confirm real inference-time VRAM/performance numbers against this
   machine before assuming feasibility beyond the "should be fine"
   assessment above.

Once these are resolved, this needs a proper implementation plan before
any code gets written — pick up with that process in the fresh session.
